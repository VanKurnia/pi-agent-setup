### 2.2 Per-module overhead dominates boot cost (measured)
Probe: identical total code as 74 chained small modules vs 5 large modules, warm cache,
`moduleCache: false`:

So jiti pays roughly 1.5-3 ms PER MODULE regardless of size. 74 eager modules x ~3.2 ms
is the whole ~235 ms. This is why merging modules genuinely works, and why deleting dead
code or shrinking config line counts does NOT move boot time at all.
Tooling: `.script/bench-timings.mjs` subtracts the one-time jiti loader init from the first
module import and reports it separately. Read the header of that file before trusting rows.

## 3. THE MERGER TECHNIQUE THAT ACTUALLY WORKED

`tmp/merge-ts.mjs` (still on disk). Regex renaming DOES NOT WORK — it cannot tell a
module-level `start` from a function parameter named `start`, and it destroyed a 10k-line
file. What works, and all of these were required in this order:

1. Line-based statement scanner (brace/paren depth, ending on `;` or `from "..."`).
   Never run a `[\s\S]*?` regex across a whole file: string literals containing
   `from "` match and get eaten.
2. Use the TypeScript compiler API for symbol identity:
   `ts.createProgram({ rootNames, options })`, `checker.getSymbolAtLocation`,
   and `checker.getAliasedSymbol` for import aliases. Rename by SYMBOL, not by text.
3. `VariableStatement` has no `.name`. Walk `declarationList.declarations`, otherwise
   every `export const` is invisible and duplicate detection silently misses them.
4. Exclude `ImportDeclaration` / `ExportDeclaration` ranges from identifier retargeting.
   Otherwise `export { a as b }` is rewritten to `export { a as a }` and the alias vanishes.
5. Namespace member access is TWO node kinds: `PropertyAccessExpression` for values and
   `QualifiedName` for types (`presentation.PresentationConfig`). Handle both.
6. Names declared twice in the SAME file are overloads / declaration merging. Never rename
   them apart; remap only the first occurrence.
7. When a name is declared in several modules, the EXPORTED one keeps the plain name and
   the locals get `$<module>` suffixes — otherwise every consumer outside the group breaks.
8. Relative imports pointing OUTSIDE the group must be re-emitted merged (dedupe by
   specifier), or the same identifier is imported twice. But relative RE-EXPORTS
   (`export { x } from "./outside.ts"`) must be KEPT as re-exports — feeding them through
   the import parser invents a default import literally named `export`.
9. A renamed slug must be a valid identifier: sanitize `-` etc., or you emit
   `ToolDisplayConfig$tool-display$types` and get a parse error.
10. Local re-exports (`export { x };`) of an unexported local must be preserved, and as
    `export type { ... }` when the symbol is a type (isolatedModules rejects otherwise).
11. Verify export parity before deleting anything:
    `node tmp/check-exports.mjs <merged> <original...>` must report `missing from merged: none`.
12. Feed files in dependency order; function declarations hoist but `const` does not, so
    a module used at top level by another must come earlier (`HOST_TEMPLATE_VARIABLES`
    broke when config.ts was emitted first).

Result with all 12 in place: `tool-display.ts` = 19 modules -> 1 file, 10,123 lines,
typecheck clean, export parity 148/148, zero extras. That part is real and reproducible.
`config.ts` = 12 modules -> 1 file, 4,174 lines, typecheck clean, parity missing=0.
`ui.ts` = the merge that failed on rule 8 above, before the fix was exercised.
